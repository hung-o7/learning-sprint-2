# Reflection

Before we started the second learning sprint, I had some background knowledge of bytes and buffers from CPRE 288. In CPRE 288, we were tasked with programming a Roomba using C code. In this class, we were taught some of the basics of C programming, including buffer capacity. I remember one example was ensuring that we knew when to use ints, doubles, and floats when calculating numbers, since there was not a lot of random-access memory (RAM) available on these robots. For example, if we only used doubles, we might have hit our robot's memory constraints. We had to be careful when deciding how to proceed, ensuring that if a variable did not need more memory, we would assign it a data type that used fewer bytes. My partner and I took this warning seriously and were very careful moving forward. We attempted to predict how much space certain variables would require and whether they would need more or less memory. We were very successful in making these predictions and were able to pass the class without exceeding our memory constraints.

I never would have imagined that the absence of buffer boundaries could pose a security concern. In the back of my mind, it was just something we had to think about when coding with limited RAM. Working through the bytes one by one with the assistance of AI really helped me understand and visualize how buffers are not just about making code work in low-level environments, but can also play a major role in the security of the code we create.

My first test was seeing how an off-by-one situation is handled without the use of a bounded copy. Since it was off by one, the null terminator could overwrite part of the saved frame pointer, potentially affecting information used to control the program. Next, I decided to test out the overwrite method without the use of a bounded copy. With an 8-byte buffer capacity, 16 characters were written. The first 8 characters went into the local character buffer, in the app’s simulated layout, the next 4 characters went into the saved frame pointer, the following 4 characters went into the return address, and finally, the null terminator fell into adjacent memory. The information had now spilled over and overwritten data used to manage function calls and program execution, which could lead to crashes, incorrect behavior, and security concerns… scary. Finally, I reran each experiment using a bounded copy, which prevented any characters from spilling over and kept the information used for function calls and program execution from being overwritten, but this came at the cost of losing some of the ending characters of the string I wanted to copy over to this space. This experience helped me visualize and understand how data can spill over into unexpected areas, potentially causing major security concerns during code execution.
